# LiteLLM gateway, routing and fallback

**G09-L03 · Intermediate · 105 min including practice**

## Learning objective

Unify provider access and enforce gateway policies.

## Concept notes

LiteLLM offers a Python SDK and proxy gateway with provider abstraction, routing, virtual keys, budgets and observability features. Retry/fallback policies must distinguish transient failures from invalid requests. Models and providers have different capabilities and token accounting.

## Worked scenario

Route two configured model deployments behind a common alias and simulate rate limiting.

## Common mistake

Retrying non-idempotent side effects or switching models that do not support the required schema.

## Practice exercise

Create a gateway configuration template and test mock fallback behavior.

**Acceptance criteria:** Log selected model, failure reason, latency and cost metadata without secrets.

## Deeper theory and design

LiteLLM can provide normalized model access and a proxy/gateway for routing, budget and observability. Fallback should distinguish retryable failures from invalid requests or policy rejection. Retrying non-idempotent operations or partially streamed outputs requires care.

## Debugging clinic

Fallback silently changes model capabilities or data region. Enforce equivalent policy constraints and disclose chosen model in trace.
