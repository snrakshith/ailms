# G06 — LangChain and LangGraph orchestration

## Chapter objectives

- Use chat models, prompts, structured outputs, retrievers and tools as composable interfaces.
- Represent a workflow as typed shared state with deterministic transitions.
- Route by state and merge independent branches safely.
- Build bounded loops, resumable state and human approval gates.

## G06-L01 — LangChain components and integration boundaries

### Core concept

LangChain integrates providers, retrievers, messages and agent components. Separate domain logic from framework adapters so tests can use fakes and migration is easier. Keep configuration and secrets outside prompts.

### Theory and reasoning

LangChain provides composable model, prompt, parser, retriever and tool abstractions; application contracts should avoid coupling core domain logic to provider response objects. A fake adapter supports deterministic testing and provider failure simulation.

### Worked scenario

Build a prompt-to-model-to-validated-output pipeline with a mock model first.

### Design and verification

Leaking provider exceptions or message classes into business logic makes migration and error handling brittle; normalize at boundary.

### Practice

Implement an adapter and swap a fake for one configured model.

Acceptance: Tests run without network; provider failures return controlled errors.

## G06-L02 — LangGraph state, nodes, edges and sequential workflow

### Core concept

LangGraph represents stateful workflows as nodes and edges. Nodes return state updates; edges define transitions. A sequential workflow follows a known order and is appropriate when the steps are predictable.

### Theory and reasoning

A LangGraph workflow consists of typed state, nodes returning state updates and edges that define transitions. Sequential execution is deterministic when nodes are deterministic; state updates and reducers define merge semantics. Graph compilation and invocation are separate steps.

### Worked scenario

Build validate -> retrieve -> generate -> finish using typed state.

### Design and verification

Mutating shared state in place obscures replay behavior. Return explicit updates and type-check state keys.

### Practice

Create a two-node offline graph and test the final state.

Acceptance: Each node has a clear state contract and can be unit-tested.

## G06-L03 — LangGraph conditional and parallel workflows

### Core concept

Conditional edges choose a destination using state; parallel branches execute independent work and need reducers or explicit merge contracts for concurrent state updates. Fan-out and fan-in should be bounded.

### Theory and reasoning

Conditional edges choose routes from state; parallel branches may concurrently update state and require reducers for shared keys. Deterministic reducers should be associative where possible; ordering should be explicit rather than inferred from execution completion.

### Worked scenario

Route invalid inputs to rejection; run keyword and vector retrieval in parallel and merge IDs.

### Design and verification

Parallel nodes writing same key without reducer may error or overwrite. Define merge contract and test fan-in under reordered completion.

### Practice

Construct a mock router and two parallel branches with a deterministic reducer.

Acceptance: Both branches contribute exactly once; invalid routes terminate.

## G06-L04 — LangGraph iterative workflows, checkpointing and HITL

### Core concept

Iterative graphs revisit nodes until a quality or budget condition; checkpointing persists graph state by thread. Human-in-the-loop interrupts pause at controlled points and resume with a decision. Side effects must be idempotent across replay.

### Theory and reasoning

A checkpoint persists graph state by execution/thread identity. Human interruption suspends execution and resumes with a decision; replay may re-execute code before interrupt depending on implementation. External effects must be idempotent and occur after authorization.

### Worked scenario

Pause a proposed write action for approval, then resume only if authorized.

### Design and verification

Performing a write before interrupt can duplicate it after resume. Place side effects behind approval and transactional idempotency.

### Practice

Build a review gate and test approve, reject and resume cases.

Acceptance: No write occurs before approval; duplicate resume does not duplicate side effects.
