# G04 — Advanced RAG patterns

## Chapter objectives

- Compare model-trained reflection signals with application-level grading loops.
- Use retrieval-quality assessment to trigger corrective retrieval.
- Design bounded correction of unsupported or incomplete answers.
- Allow a bounded agent to select retrieval tools and decompose queries.

## G04-L01 — Self-reflective RAG and Self-RAG

### Core concept

Self-RAG is a research method using learned reflection tokens to control retrieval and critique generations. Application-level self-reflective RAG may instead use separate graders for evidence relevance, grounding and answer usefulness; these are related but not identical.

### Theory and reasoning

Self-RAG research trains a model to retrieve and emit reflection tokens; a generic self-reflective RAG application instead adds an external grader and retry loop. They are related but not identical. Reflection only improves quality if feedback is informative and independently checked.

### Worked scenario

Retrieve evidence, grade relevance, generate and run a grounding check before returning an answer.

### Design and verification

Letting a model approve its own unsupported answer can reinforce hallucination. Use gold examples and external evidence checks; measure false-accept rate.

### Practice

Implement a bounded grade-and-retry loop with a deterministic mock grader and evaluate false accepts.

Acceptance: Stop on max attempts and preserve evidence for every decision.

## G04-L02 — Corrective RAG (CRAG)

### Core concept

The CRAG research approach evaluates retrieved-document quality and triggers corrective actions, including knowledge refinement and possible external search. An application-inspired implementation may route to rewrite, alternate index or approved search when evidence is weak.

### Theory and reasoning

CRAG assesses retrieval quality and selects corrective actions, including knowledge refinement or external search in the research approach. A three-way router can represent strong, ambiguous and weak evidence; thresholds should be calibrated rather than treated as universally valid. External retrieval expands the trust boundary.

### Worked scenario

Grade retrieval as strong, weak or ambiguous; route weak cases to a second trusted corpus.

### Design and verification

A fallback leaks confidential queries to an external service or inserts stale documents. Authorize sources and redact/deny queries before retrieval; retain provenance.

### Practice

Implement a three-way retrieval-quality router with an offline fallback corpus.

Acceptance: Route tests cover strong, weak, ambiguous and unavailable fallback cases.

## G04-L03 — Self-corrective RAG and iterative verification

### Core concept

Self-corrective RAG is a broad application pattern rather than a single universal algorithm. Verify claims against evidence, revise or retrieve again and stop when quality gates pass or budget is exhausted.

### Theory and reasoning

Self-corrective RAG verifies generated claims, not just retrieval quality. Correction may revise unsupported claims, retrieve missing evidence or abstain. Iteration needs a bounded budget and a progress signal; repeated same evidence is not progress.

### Worked scenario

Detect missing citation support in a generated answer and regenerate only unsupported claims.

### Design and verification

An unbounded verifier loop increases cost while never resolving a missing document. Add max attempts, evidence-change check and terminal failure state.

### Practice

Implement a verifier with max three attempts and an explicit abstain state.

Acceptance: All runs terminate; unsupported claims are removed or flagged.

## G04-L04 — Agentic RAG and routing

### Core concept

Agentic RAG uses a model or controller to choose retrieval actions, sources or subqueries. It can support multi-hop questions, but introduces extra latency, cost and failure modes. Authorization must be enforced outside the model.

### Theory and reasoning

Agentic RAG uses a policy or model to choose whether/where/how to retrieve and when to finish. Deterministic routing is often cheaper and easier to audit; agent selection is helpful only if diverse requests benefit from adaptive retrieval. Tool permissions remain external.

### Worked scenario

Route a policy question to internal search and a product question to a catalog tool.

### Design and verification

Agent repeatedly searches irrelevant indices and misses SLA; impose route/tool budget, timeouts and explicit terminal conditions.

### Practice

Compare deterministic routing with a bounded agent on a mixed question set.

Acceptance: Report route accuracy, recall, tool count and cost proxy.
