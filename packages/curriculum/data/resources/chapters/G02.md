# G02 — Prompt and context engineering

## Chapter objectives
- Design examples for task specification and contextual generalization.
- Validate generated objects at the application boundary.
- Use role/context and concise reasoning artifacts without treating reasoning text as proof.
- Explain how messages become model-specific serialized token sequences.
- Treat prompts and context as versioned software artifacts.

## G02-L01 — Zero-shot, one-shot and few-shot prompting

### Core concept
Zero-shot uses instructions without examples; one-shot supplies one demonstration; few-shot uses multiple representative examples. Examples guide output style and decision boundaries but do not guarantee deterministic inference or generalization.

### Theory and reasoning
Zero-shot gives task and instructions without demonstrations; one-shot adds one example; few-shot provides multiple representative examples. Examples specify behavior and format but can introduce ordering and label biases. Deterministic inference is a decoding/property issue, not a consequence of one-shot prompting.

### Worked scenario
Classify support messages using zero, one and several examples and compare held-out accuracy.

### Design and verification
An example copies test content or contains incorrect labels, inflating performance or teaching wrong patterns. Audit overlap and label quality.

### Practice
Build a labeled holdout and compare all three prompt variants with fixed decoding settings.

Acceptance: Report accuracy, format errors and example-selection criteria.

## G02-L02 — Structured output, few-shot schemas and Pydantic

### Core concept
Structured generation may use JSON schema constraints or tool arguments; few-shot examples illustrate semantic mappings. Pydantic validates typed Python objects, can reject extra fields and express constraints. Valid structure does not guarantee truthful content.

### Theory and reasoning
Structured output separates syntax, schema and semantic correctness. Pydantic can reject unexpected fields and validate ranges; JSON Schema or constrained decoding may reduce invalid syntax where supported. Few-shot examples illustrate expected output but cannot replace validation.

### Worked scenario
Extract an invoice object with required currency, total and item fields.

### Design and verification
Valid JSON can have invented evidence or unsupported confidence. Add business checks and source verification after schema validation.

### Practice
Define a strict Pydantic schema and test malformed, missing and extra fields.

Acceptance: Invalid payloads fail safely; valid payloads serialize predictably.

## G02-L03 — Persona prompting, reasoning prompts and prompt injection

### Core concept
Persona prompts establish tone, audience and constraints, not genuine expertise. Chain-of-thought prompting is a research approach to eliciting intermediate reasoning; applications can instead request concise justification, verifiable calculations or structured plans. Untrusted content must remain data.

### Theory and reasoning
Persona prompts specify tone, role and audience, not real authority or identity. Reasoning prompts can request concise explanations, verifiable intermediate results or use of tools; hidden chain-of-thought is not required or necessarily faithful. Treat retrieved and user-provided content as untrusted data.

### Worked scenario
Ask a tutor to return an answer plus a short evidence-based explanation, then test adversarial user text.

### Design and verification
A persona says it may ignore access policy; enforce permission in application code, not a prompt claim.

### Practice
Compare persona vs neutral prompts and test input that asks to ignore instructions.

Acceptance: Evaluate correctness and instruction adherence using external checks.

## G02-L04 — Prompt serialization: ChatML, Alpaca and INST

### Core concept
ChatML-style formats use role delimiters; Alpaca-style templates often use Instruction/Input/Response sections; [INST]-style formats mark instruction boundaries in certain model families. Exact control tokens and role rules vary by tokenizer and model revision.

### Theory and reasoning
ChatML, Alpaca and INST represent families of prompt serializations; exact markers, roles, EOS and generation suffixes vary across checkpoints. Training and inference formatting must align. Double-adding special tokens can degrade model behavior.

### Worked scenario
Inspect tokenizer.apply_chat_template on system, user and assistant messages and compare conceptual templates.

### Design and verification
Manually concatenating a generic INST prompt for an incompatible model yields malformed role boundaries. Use its provided chat template and test round trip.

### Practice
Render two actual model templates and identify role and generation markers.

Acceptance: Use the tokenizer's own template and document supported roles.

## G02-L05 — Prompt versioning, testing and context engineering

### Core concept
A prompt includes instructions, examples, retrieved evidence and output contracts. Context engineering selects, orders and truncates inputs; tests track behavior across model or prompt changes. Stable schemas and adversarial fixtures support regression testing.

### Theory and reasoning
A prompt is a versioned dependency together with model revision, decoding, schema, tools and context assembly policy. A regression harness uses fixed inputs and explicit expected behavior. Context engineering controls what evidence enters the prompt and in which order.

### Worked scenario
Version two prompts with a dataset of normal, ambiguous and injection attempts.

### Design and verification
Changing model and prompt simultaneously makes attribution impossible; isolate changes and repeat stochastic runs.

### Practice
Create a prompt registry record with model revision, template hash and evaluation results.

Acceptance: Regression report compares one variable at a time and tracks cost and latency.
