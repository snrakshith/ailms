## F01-L01 — Python environments and notebooks

### Core concept

An environment isolates dependencies; a notebook keeps code and outputs in cells but execution order can hide state. uv can manage environments and lock dependencies; pip installs packages into the active interpreter.

### Theory and reasoning

A virtual environment has its own site-packages and Python executable; a notebook kernel is a separate process that must point to that interpreter. Lockfiles capture resolved dependencies rather than merely requested names. Restarting clears variables and imports, revealing hidden dependencies on cell order.

### Worked scenario

Create a Python 3.11 environment, install NumPy and restart the kernel before running all cells.

### Design and verification

A notebook succeeds only after running cell 9 first. Move definitions before use, restart, then run all; check executable rather than blindly reinstalling.

### Practice

Create an environment, run a notebook from a fresh kernel and record Python/package versions.

Acceptance: The notebook runs top-to-bottom without manual state; the interpreter matches the environment.

## F01-L02 — Python data types, control flow and functions

### Core concept

Functions encapsulate transformations. Mutable lists and dictionaries can be modified in place; tuples are immutable containers. Type hints document expected inputs but do not enforce them at runtime.

### Theory and reasoning

Lists preserve order, dictionaries map unique hashable keys, and sets deduplicate hashable values. Counting is a reduction: each record changes one accumulator entry. Make missing-label policy explicit; purity is useful because independent calls are easier to test.

### Worked scenario

Turn a list of measurement records into a dictionary of counts by category.

### Design and verification

A default argument `out={}` accumulates previous calls. Move initialization into the function; call twice and verify independent results.

### Practice

Implement a count-by-category function handling empty input and missing labels.

Acceptance: Empty input returns an empty dictionary; repeated calls are independent.

## F01-L03 — NumPy arrays, broadcasting and vectorization

### Core concept

An ndarray stores homogeneous values; broadcasting aligns dimensions from the right when sizes match or one is 1. Vectorized operations avoid Python loops and exploit compiled kernels.

### Theory and reasoning

For matrix X of shape (n,d), column mean has shape (d,), which broadcasts across rows. Standardization z=(x−μ)/σ is scale-sensitive; a constant feature contains no variation. Fit statistics only on training data when a model is involved.

### Worked scenario

Normalize each feature of a matrix using column means and standard deviations.

### Design and verification

A zero variance feature produces NaN; using axis=1 instead of axis=0 normalizes samples, not features. Verify shape and axis explicitly.

### Practice

Standardize a 3-column matrix including a constant column, preserving its shape.

Acceptance: Nonconstant columns have near-zero mean and unit variance; the constant column remains finite.

## F01-L04 — Pandas, data cleaning and EDA

### Core concept

DataFrames associate named columns with rows. Missingness, duplicates, types and join cardinality affect downstream analysis. Exploratory data analysis (EDA) uses summaries and plots to discover patterns, not to establish causation.

### Theory and reasoning

EDA is an audit of the data-generating process, not just plotting. Join cardinality determines whether a merge multiplies rows; missingness can be informative or accidental. A label distribution needs counts and proportions and should be stratified when relevant.

### Worked scenario

Inspect a customer table, flag missing ages, join transactions by customer ID and plot label frequency.

### Design and verification

A many-to-many merge doubles positive cases and inflates apparent performance. Assert expected cardinality and audit duplicated keys before training.

### Practice

Create a data-quality report with missing counts, duplicate keys and label distribution.

Acceptance: Report row counts before and after joins and identify nonunique keys.

## F01-L05 — Git, testing and reproducible experiments

### Core concept

Git tracks source changes; dependency locks and data/model versions record experimental context. Unit tests verify small functions, while integration tests cover interfaces. Random seeds improve repeatability but do not guarantee identical GPU computation.

### Theory and reasoning

Reproducibility requires code version, input identity, environment and configuration. A fixed seed helps but cannot guarantee determinism across libraries or hardware. Tests should verify behavior, not implementation details; secrets belong outside tracked files.

### Worked scenario

Commit a feature transformer and test empty, missing and valid values with pytest.

### Design and verification

A test passes alone but fails in the suite due to mutable global state. Create fixtures per test and remove shared mutation; rotate any credential accidentally committed.

### Practice

Write three tests for a numerical feature transformer and document a run command.

Acceptance: Tests pass independently; secrets are not in the repository.
