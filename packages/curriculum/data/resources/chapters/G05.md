## G05-L01 — Tool calling and tool-use agent pattern

### Core concept
A tool call is structured data requesting an external operation. The application validates arguments, authorizes execution, returns results and manages timeouts. Read and write tools have different risk profiles; side effects need idempotency and approvals.

### Theory and reasoning
Tool calling is a typed request to an external capability. The model proposes arguments; the application validates schema, user scope, authorization and side-effect policy before execution. Results are untrusted observations, not instruction authority.

### Worked scenario
Expose a read-only inventory lookup with typed item ID and structured result.

### Design and verification
A valid JSON argument references another tenant's record. Enforce tenant from authenticated context, not caller-supplied fields.

### Practice
Implement a tool registry, argument validation and unknown-tool error handling.

Acceptance: Invalid and unauthorized calls do not execute; errors are structured.

## G05-L02 — ReAct, planning and action-observation loops

### Core concept
ReAct is a research pattern interleaving reasoning with actions and environment observations. An application can expose concise action decisions and tool results rather than private reasoning traces. State, stop conditions and budgets control the loop.

### Theory and reasoning
ReAct research interleaves reasoning and acting; application implementations can expose action and observation traces without exposing private reasoning. Unlike fixed chains, policy decisions adapt to observations. Planning can propose steps while execution validates each individually.

### Worked scenario
Use a controller to choose between lookup, calculator and final answer based on observations.

### Design and verification
A model repeats the same tool indefinitely; detect repeated calls, budget attempts and terminate with a useful error.

### Practice
Build a mock loop that stops after four actions or a valid final result.

Acceptance: Trace records action name, sanitized arguments, observation and termination reason.

## G05-L03 — Reflection and evaluator-optimizer agents

### Core concept
A reflection loop creates a candidate, critiques it against a rubric and revises. An evaluator-optimizer workflow separates generation from grading; a deterministic validator may be better for objective constraints. Bound iterations and compare with one-pass baseline.

### Theory and reasoning
Reflection generates critique of a candidate; evaluator-optimizer separates quality scoring from revision. Improvement is not guaranteed, particularly when judge and generator share biases. Compare against one-pass baseline under same test set and budget.

### Worked scenario
Generate a short summary, grade missing required facts, then revise once.

### Design and verification
A judge gives higher score to verbose but wrong answers; anchor rubric to facts and run blind human review of disagreements.

### Practice
Build a mock rubric checker and compare one-pass versus iterative outputs.

Acceptance: Track improvement, revision count, failure rate and stop reason.

## G05-L04 — Multi-agent systems and orchestration

### Core concept
Multiple agents can divide tasks or specialize tools; a supervisor coordinates routing and state, while handoff transfers responsibility. Coordination costs and inconsistent state can outweigh benefits. Shared contracts and permissions are necessary.

### Theory and reasoning
Multi-agent systems partition responsibility among workers, often supervisor, specialists or peer roles. Shared state needs conflict-resolution and ownership rules; fan-out increases latency/cost and may propagate errors. Independent verification is preferable to agent consensus alone.

### Worked scenario
A research coordinator delegates retrieval and verification to separate workers then merges evidence.

### Design and verification
Giving each specialist every tool defeats least privilege. Restrict capabilities per worker and validate merged provenance.

### Practice
Implement a supervisor with two mock specialists and bounded fan-out.

Acceptance: Each worker has narrow tools; merge resolves conflicts and records provenance.
