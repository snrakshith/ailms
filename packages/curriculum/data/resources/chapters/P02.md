# P02 — Production reliability and responsible AI

## Chapter objectives

- Detect changes in inputs, behavior and operational health.
- Build privacy, documentation and risk controls into AI lifecycle.
- Design a production AI workload with cost and reliability budgets.

## P02-L01 — Monitoring, drift, reliability and retraining

### Core concept

Data drift changes input distribution; concept drift changes the relationship between inputs and targets; label delays limit immediate accuracy monitoring. Track latency, errors, resource use and data quality; retrain only after validated diagnosis.

### Theory and reasoning

Data drift changes input distribution, concept drift changes relationship between input and target, and service degradation changes reliability. Drift signals do not prove quality degradation; delayed labels and seasonal shifts complicate monitoring. Alerts need owners and action.

### Worked scenario

Simulate a shifted feature distribution and monitor prediction scores.

### Design and verification

Automatically retraining on every drift alert may worsen performance; investigate data integrity, seasonality and actual quality first.

### Practice

Create drift and service alerts, escalation thresholds and a rollback plan.

Acceptance: Alerts have actionable ownership, context and known false-positive limitations.

## P02-L02 — Responsible AI, governance and security

### Core concept

Governance covers data rights, consent, access, model cards, risk assessment, evaluation and incident response. Threat models include training-data poisoning, extraction, adversarial inputs and unauthorized agent actions. Requirements depend on jurisdiction and application.

### Theory and reasoning

Responsible AI governance spans data rights, privacy, model limitations, fairness, safety and accountability. Risk registers map harms to controls, validation and ownership; auditability requires retained evidence with access and retention limits. Governance is use-case-specific.

### Worked scenario

Create a model card and risk register for a support assistant with sensitive data.

### Design and verification

A checklist with no test evidence or owner cannot demonstrate effectiveness; require concrete evidence and signoff.

### Practice

Draft data inventory, model limitations, approval checkpoints and incident procedure.

Acceptance: Every risk has mitigation, owner and validation evidence.

## P02-L03 — Cloud architecture, scaling and deployment trade-offs

### Core concept

Separate API, model serving, storage, queueing and observability. Batch processing favors throughput; online inference favors latency. AWS examples include S3, ECS/EKS, SageMaker and managed databases; equivalent services exist on other clouds.

### Theory and reasoning

Cloud deployment balances availability, throughput, cost, latency and isolation. Separate API/auth, inference workers, registry/storage, network and monitoring. Autoscaling needs meaningful queue/latency signals and downstream quotas; recovery objectives guide backup and failover.

### Worked scenario

Design a RAG service with tenant-scoped retrieval, gateway and async ingestion queue.

### Design and verification

Autoscaling workers without provider quota or budget limits amplifies failures/cost. Set concurrency, backpressure, retry budgets and alarms.

### Practice

Diagram architecture, forecast cost drivers and define rollback and recovery objectives.

Acceptance: Architecture includes identity, encryption, limits, monitoring and failure isolation.
