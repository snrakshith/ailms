# G10 — LLM and agent evaluation

## Chapter objectives
- Design reliable agent and LLM evaluation beyond final answer accuracy.
- Integrate metric-based evaluations into a test workflow.
- Measure retrieval and generation with appropriate reference data.
- Run test matrices across prompt/provider combinations and adversarial cases.
- Make LLM applications measurable and govern releases.

## G10-L01 — Agent evaluation, datasets and LLM-as-judge

### Core concept
Evaluate task success, tool selection, arguments, trajectory, latency, cost, safety and human intervention. LLM-as-judge uses a model to score a rubric; position bias, verbosity bias and correlated errors require human calibration and deterministic checks where possible.

### Theory and reasoning
LLM-as-judge applies a model to rubric scoring, pairwise preference or classification; it can be biased by position, verbosity and model family. Human-labeled anchors, randomized order and agreement estimates help calibrate judge behavior. Judge score is one signal, not ground truth.

### Worked scenario
Compare an answer judge with human labels and measure agreement on a held-out set.

### Design and verification
A judge rewards longer answer without checking evidence. Require claim-level anchors and independent human sample.

### Practice
Create a rubric with anchors, run pairwise comparisons in both orders and review disagreements.

Acceptance: Report agreement, judge config and failure cases; do not use judge score alone.

## G10-L02 — DeepEval for LLM and agent regression tests

### Core concept
DeepEval provides evaluation constructs for model outputs and various task-specific metrics. Use synthetic and human-authored cases, deterministic assertions for tool contracts and configured model judges for semantic metrics. Judge calls may incur cost.

### Theory and reasoning
DeepEval supports LLM test cases and metrics with version-dependent configuration; some semantic metrics invoke an LLM judge. Deterministic contract tests should remain runnable offline, while judge-backed tests require credentials, budgets and calibration.

### Worked scenario
Create cases for grounded answers and unsupported claims using a configured evaluator.

### Design and verification
Treating judge-dependent tests as offline makes CI flaky and costly. Separate jobs and mark skipped explicitly when no credentials.

### Practice
Write an offline exact-match test and a separate opt-in DeepEval semantic test.

Acceptance: Offline CI works without keys; judge-backed checks log thresholds and model.

## G10-L03 — Ragas for RAG evaluation

### Core concept
Ragas offers metrics for retrieval and answer assessment, with metric-specific required fields and judge/embedding dependencies. Use human-reviewed examples to calibrate and distinguish context recall, precision and faithfulness.

### Theory and reasoning
Ragas offers RAG-oriented metrics with required input fields that differ by metric and release. Faithfulness assesses support by retrieved contexts, while retrieval relevance/recall and answer correctness address other stages. Metric outputs depend on judge and embedding settings.

### Worked scenario
Evaluate retrieval evidence against reference answers for a small question set.

### Design and verification
Passing reference text as retrieved context artificially improves faithfulness; keep actual retrieval evidence separate from reference answer.

### Practice
Prepare a dataset with user input, retrieved contexts, response and reference; select appropriate metrics.

Acceptance: Report per-metric required columns, model and sample-level failure analysis.

## G10-L04 — Promptfoo for prompt/model evaluation and red teaming

### Core concept
Promptfoo supports declarative evaluation configurations, provider/prompt matrices and assertions. Some checks are deterministic; judge-based assertions use a configured model. Security testing needs permission, scoped targets and non-sensitive fixtures.

### Theory and reasoning
Promptfoo evaluates prompt/model configurations against cases and assertions, including adversarial evaluations. Provider execution may cost money or send data externally. Deterministic checks and semantic checks have different failure modes.

### Worked scenario
Evaluate two support prompts with regex/schema assertions and a rubric.

### Design and verification
Only evaluating happy paths overlooks injection and format failures; keep adversarial holdouts and fail closed on protected action.

### Practice
Create a local evaluation configuration for normal and adversarial inputs with pass criteria.

Acceptance: Report passing and failing cases and keep secrets in environment variables.

## G10-L05 — Observability, traces, evaluation gates and cost

### Core concept
Trace spans connect model calls, retrieval and tools; metrics include latency percentiles, token usage, cost, success and safety violations. Release gates compare quality and operational budgets against a baseline. Redact sensitive input/output and restrict trace retention.

### Theory and reasoning
Observability records requests, stages, model/tool selections, latency, token use and outcomes, with sensitive fields minimized. Evaluation gates compare candidate against baseline with explicit metrics and sample sizes. Production traces support triage but may contain private content.

### Worked scenario
Compare two RAG versions by recall@k, grounded answer rate, p95 latency and token cost.

### Design and verification
Averages hide tail latency and failures; use percentiles and per-slice results, redact prompt/response logs and limit retention.

### Practice
Define an evaluation dashboard and a CI gate for four metrics with rollback criteria.

Acceptance: Each metric has dataset, threshold, owner and failure action.
