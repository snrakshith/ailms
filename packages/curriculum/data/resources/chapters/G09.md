## G09-L01 — FastAPI, Pydantic and async inference APIs

### Core concept
FastAPI maps HTTP requests to typed Python handlers; Pydantic defines data contracts. Async I/O helps concurrent network-bound calls; blocking CPU/GPU operations may require workers or separate inference services. Authentication, limits and timeouts belong at service boundaries.

### Theory and reasoning
FastAPI maps HTTP requests to validated Pydantic models and response schemas. Async endpoints improve concurrency for awaited I/O, not CPU-bound inference by themselves. Timeouts, exception mapping, limits and health/readiness checks are separate concerns.

### Worked scenario
Expose a typed prediction or chat endpoint and test malformed inputs.

### Design and verification
Calling blocking inference directly inside async endpoint stalls event loop; move CPU work to appropriate executor or separate inference service.

### Practice
Build a FastAPI service with health and validated inference endpoints.

Acceptance: Tests cover success, invalid input, timeout and error responses.

## G09-L02 — Streaming responses: SSE, chunks and cancellation

### Core concept
Server-sent events use text/event-stream and framed events; clients should handle partial content, error and completion events. Provider streaming, application streaming and UI rendering are separate layers. Cancellation and backpressure limit wasted resources.

### Theory and reasoning
SSE uses UTF-8 events separated by blank lines, typically `event: delta` and `data: ...`. Streaming lowers time-to-first-token but not necessarily total latency. Cancellation should propagate to upstream generation; once headers sent, errors need in-stream semantics.

### Worked scenario
Stream a mock token sequence using FastAPI StreamingResponse and detect disconnect.

### Design and verification
A generator catches cancellation as generic error and keeps generating; ensure cleanup in finally and test canceled iteration.

### Practice

Acceptance: Events are framed correctly; cancellation stops unnecessary work.

## G09-L03 — LiteLLM gateway, routing and fallback

### Core concept
LiteLLM offers a Python SDK and proxy gateway with provider abstraction, routing, virtual keys, budgets and observability features. Retry/fallback policies must distinguish transient failures from invalid requests. Models and providers have different capabilities and token accounting.

### Theory and reasoning
LiteLLM can provide normalized model access and a proxy/gateway for routing, budget and observability. Fallback should distinguish retryable failures from invalid requests or policy rejection. Retrying non-idempotent operations or partially streamed outputs requires care.

### Worked scenario
Route two configured model deployments behind a common alias and simulate rate limiting.

### Design and verification
Fallback silently changes model capabilities or data region. Enforce equivalent policy constraints and disclose chosen model in trace.

### Practice

Acceptance: Log selected model, failure reason, latency and cost metadata without secrets.

## G09-L04 — Guardrails, prompt injection, privacy and HITL

### Core concept
Input validation, output schema checks, tool authorization, PII handling, content policy checks and human review provide complementary defenses. Prompt injection treats untrusted content as attempted instructions; no single filter guarantees protection. Streaming may require buffering or incremental checks.

### Theory and reasoning
Guardrails layer input validation, prompt-injection resistance, tool authorization, output checking and human review. No classifier or prompt alone eliminates attacks. Sensitive data policy and fail-closed protected actions must be enforced outside model generation.

### Worked scenario
Block unauthorized writes even when a model claims approval and mask sensitive fields in logs.

### Design and verification
Using model decision as sole authorization creates bypass. Require authenticated policy checks and fail closed on unavailable policy service.

### Practice
Threat-model an agent and build tests for injection, unauthorized actions and sensitive output.

Acceptance: Fail closed for protected actions; escalation and audit events are recorded.
