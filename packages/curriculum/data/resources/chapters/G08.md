## G08-L01 — Memory taxonomy: working, factual, episodic and semantic

### Core concept

Working memory is current context and state. Long-term semantic memory stores general knowledge or meaning, factual memory stores discrete facts and is often treated as a subset of semantic memory, and episodic memory records events or experiences. Procedural memory can store reusable actions or policies.

### Theory and reasoning

Working memory is temporary conversation/task state. Long-term factual memory stores propositions, episodic memory stores time-specific events, semantic memory stores generalized knowledge (these categories overlap); procedural memory stores strategies. Store consent, provenance and expiry alongside content.

### Worked scenario

Store a preference as a fact, a past support interaction as an episode and current task variables in working state.

### Design and verification

A temporary request becomes permanent preference without consent; distinguish session-only from persistable and permit correction/deletion.

### Practice

Design a memory schema with type, source, timestamp, scope and expiry.

Acceptance: Each entry has an explicit purpose and retention decision.

## G08-L02 — Memory retrieval, summarization and vector storage

### Core concept

Memory pipelines select candidates, resolve duplicates, store provenance, retrieve by relevance and recency, and inject only authorized context. Summaries compress history but may omit important details; vector search does not guarantee correct recall.

### Theory and reasoning

Vector similarity finds related content, not truth or authorization. Memory retrieval combines scope, recency, relevance and source quality; summaries are lossy and should retain provenance. Deletion must remove records, vector entries and relevant caches.

### Worked scenario

Compare raw chat history, rolling summary and retrieved memory on a follow-up question.

### Design and verification

Post-filtering results after cross-tenant retrieval may leak via logs or caches; enforce authorization in data access and test isolation.

### Practice

Implement a scoped in-memory store with update and delete operations, then add vector retrieval.

Acceptance: Two users remain isolated; deleted entries no longer appear in results.

## G08-L03 — Mem0 and persistent agent memory

### Core concept

Mem0 supports extraction, storage and retrieval of memory using configured models and vector stores. Application policy determines consent, scope, update rules and deletion. Evaluate memory precision, recall, freshness and false memories separately from answer quality.

### Theory and reasoning

Mem0 abstracts memory operations and may use model and vector backends. Its interface and storage/deletion semantics depend on version and configuration. Treat it as infrastructure, not authority to persist arbitrary sensitive conversation details.

### Worked scenario

Add a user-authorized preference under a test user ID and retrieve it for a later query.

### Design and verification

A delete only removes display record but leaves vector entry; test retrieval and storage-level deletion, including cache behavior.

### Practice

Connect Mem0 in a sandbox or implement an adapter with a fake backend; test add/search/update/delete.

Acceptance: User isolation and deletion behavior are verified; provider dependencies documented.
